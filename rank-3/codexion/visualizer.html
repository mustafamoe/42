Codexion, explained.

Build a C program that simulates coders sharing USB dongles. Each coder runs in a thread—an independent flow of work. Your job is to coordinate them so everyone can keep compiling.

Each coder needs two dongles.

Coders sit in a circle, with one dongle between each pair of neighbours. To compile, a coder must hold both dongles beside them. Then they release them, debug, refactor, and try again.

Wait for two→Compile→Debug→Refactor→ repeat
4 coders4 dongles
Before starting

The dongles are shared.

Coder 1 needs D4 and D1. Coder 2 also needs D1, so these neighbours cannot compile at the same time.

The challenge: give each coder a turn without letting two coders claim the same dongle.

Step 1 of 7

Guided example: 200 ms compile, 100 ms debug, 100 ms refactor, 200 ms dongle cooldown, 2 compiles each. Times are illustrative, not a live execution of C threads.

Compiling resets the burnout timer.

A coder must start another compilation before their deadline. Every activity and every wait uses that time. Here is coder 1’s first cycle with a 1,000 ms burnout interval:

Success: everyone reaches the goal.Stop when every coder has completed the required number of compilations.

Failure: any coder burns out.Stop the entire simulation as soon as one coder misses their deadline.

The requirements and the solution.

RequirementSolution in this project
One thread per coderEach thread repeats request → compile → release → debug → refactor. A condition variable lets it sleep while waiting and wake to check again.
Protect shared donglesA mutex locks each dongle’s state. Grant both dongles together, so a coder never holds one while waiting for the other. This prevents that form of deadlock.
Respect cooldownOn release, store ready time = now + cooldown. No coder can take the dongle before that time, even if it has no owner.
Schedule fairlyA custom heap on each dongle keeps the highest-priority request easy to find. Use FIFO or EDF. Protect a blocked priority request from repeated overtaking so it cannot be ignored forever (starvation).
Detect burnout promptlyA separate monitor thread checks each active coder’s last compile start. Print burnout within 10 ms of the deadline and tell every worker to stop.
Print and finish cleanlyLock the output so log lines never mix. On shutdown, wake waiting threads, join them, destroy synchronization objects, and free allocated memory.

FIFO or EDF: who goes first?

Two coders request the same dongle. A asks first, but B is closer to burnout.

A gets prioritythen B

FIFO means First In, First Out. A asked first, so A goes first.

How the code combines two dongle queues

One request goes into both neighbouring dongle heaps. FIFO compares arrival order. EDF compares burnout deadlines, then arrival order and coder ID.

The scheduler grants a complete pair when it is available. If the highest-priority request is blocked, at most one request sharing its dongles may pass it. Under EDF, that bypass must also leave enough time before the protected deadline. Requests using separate dongles can still run.

Both dongle mutexes are locked in ascending index order to avoid a cycle of locks. A waiting coder wakes on a signal or cooldown timeout, then checks the scheduler again.

This is the current implementation’s interpretation of combining two queues. The subject specifies FIFO/EDF per dongle but does not fully define that combination; a later evaluation sheet could require a different interpretation.
